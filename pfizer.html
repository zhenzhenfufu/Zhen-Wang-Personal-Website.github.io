HGRAC Filing Assistant

AI Agent Development Intern · Biomedical Informatics & Data, Pfizer (China) R&D Center

A regulatory filing is one of the few places where a plausible answer is worth nothing. I spent three months building the system that produces one — and more time proving it was right than building it.

Scale
10,184 records · 3,792 pages per run
Runtime
~20 min full library
Verification
1,197 records, zero discrepancies
Agents
3 built · 4 architectures scored

The problem

Before a clinical study can be filed with Chinese regulators, every record belonging to a Chinese subject has to be split into pre-randomisation and post-randomisation on a per-subject basis, then rendered into submission-grade reports. The inputs are an Excel application form written by humans, with no fixed layout, and a folder of SAS datasets. The process was done by hand, per study, by people whose time is worth more than this.

What I built

  • An end-to-end pipeline: parse the application form into a machine-readable control file, resolve each subject's randomisation date, classify every record against it, and emit compliant RTF and PDF reports. One run turned 25 SDTM datasets into 10,184 classified records across three reports totalling 3,792 pages, in about twenty minutes.
  • Per-record cascading date resolution, which fixed three systematic misclassifications the manual process had been absorbing — including a per-dataset column choice that misrouted every one of 1,800+ records in one domain, and a randomisation lookup that left 40+ screen-failure subjects unclassifiable.
  • A provenance column on every record: which date it was judged on, and what it was compared against. A reviewer who cannot read R can still check the result, which is the only kind of checking that happens in practice.
  • Report generation that survives its environment. The original design needed a headless browser to render PDFs, and the company's Linux server had none — so the route is now RTF first (which is what actually gets submitted), then browser, then LibreOffice, with the chosen path printed at startup.

Three agents, and one that was quietly wrong

  • I added three agents on top of the deterministic core — dataset reconciliation, classification review, and open-item triage — switchable between the Gemini API and a local Ollama qwen2.5 backend.
  • One of them kept misclassifying a record that the rules were unambiguous about. I found it by ablation: the model was keying on how often a date appeared and where it sat in the row, not on the rule it had been given. The same record flipped when I changed only duplication and field position — never a value.
  • The fix was to stop asking politely. The instruction became a hard constraint, and all arithmetic went back to deterministic code. That closed the last three disagreements with the reference implementation out of 90+ sampled records — 97% agreement to 100%. Three records is a small delta; the useful part is knowing why they disagreed.
  • I then scored four architectures — straight automation, ReAct, Plan-and-Execute, and a seven-role council — against a 12-criterion rubric I derived from the regulatory specification: the seven-role council reached 0.925 against 0.719 for the automation baseline. I scored it myself, one run per architecture, so treat it as an internal comparison and not a benchmark result.

How I know it is right

A colleague had independently written a classification engine for the same rules. We reconciled 13 datasets and 1,197 records line by line: zero discrepancies. That is the only independent check here — re-running the whole library two days later reproduced identical counts, which proves determinism, not correctness. His implementation, not my own reading of the specification, was treated as the definition of correct — and his code was never edited; the six places where our interfaces disagreed are worked around on my side, with the reason written at each one.

The data boundary

The agents only ever see file names, date fields, and column names. Never subject identifiers — row numbers stand in for them — never lab values, never free text. The first three stages of the pipeline do not touch the network at all, and the API key lives only in a local .Renviron, never in anything that ships.

What this is not

  • It was handed over as code plus documentation at the end of my internship, written for a department of about 200 people. Rolling it onto live studies is the team's next step, not something I can claim as done.
  • It has never run against a real study library — every number here comes from a dummy study (A1234567, 132 subjects, 25 datasets, 135,130 rows).
  • The agent features cannot run on company machines, which have no external API access. They work locally and in the demo; inside the firewall, everything except the agents is usable.
  • 24 open items still need the study team's confirmation, and 246 hand-filled cells in the application form are not automated yet.
